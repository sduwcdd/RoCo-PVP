# 阵容码解析、校验与对方阵容检索

## 依据与保留边界

协议依据为用户核查规则与 Roco Showdown 社区网页实现，不是官方协议文档：

- 页面：https://roco-showdown.com/teams
- 核查文件：https://roco-showdown.com/_next/static/chunks/2427-9b9809421a06aa9e.js
- 获取时间、原文件 SHA-256 见 `data/reference/team-code-20261025/source.json`；原实现保存于同目录。
- 精灵形态、技能和性格名称及学习条件使用当前 BWIKI 快照；代码不使用旧引擎表补值。
- 核心魔法 104002「愿力强化」、104007「进化之力」来自用户验证案例。其他 ID 保留原值、标记待核实。
- 用户自己的阵容码保存在本地，不纳入公开源码；可通过界面导入并保留本地来源。

## 独立接口

`lab.team_code.parse_team_code(code, catalog)` 返回原码、协议/队伍类型、核心魔法、具体形态、血脉、原性格、后天方向修正、最终方向、四个有序技能槽、原始资质标记、数据快照和分类诊断。每个问题含槽位、字段、原值与依据。

固定宽度字段按字符表累积为整数，不能拆 `~`、不能作普通 Base64 字节流。仅核心魔法、资质标记、技能允许**整个原字段都是 `0`** 时解释为零，例如 `00000` 为零；`0000~` 不满足该规则。普通字段的 `0` 仍是字符表索引 52。

零技能槽保留位置，包括末尾空槽。重复技能不去重，未知 ID 不替换。重复资质标记保留如 `[80,80,80]`，六维真实数值全部保持未知。首领血脉不改变精灵形态。

问题分为 `format_error`、`database_conflict`、`unverified`、`user_confirmed_error`。当前数据库冲突不等同游戏非法。未知/不唯一的精灵技能、重复技能、无法映射性格以及用户确认错误会阻止导入。已知 ID 的条件冲突或待核实条目可显式导入**研究配置**，保留诊断，绝不宣称通过合法性认证。阵容码缺少完整资质和可核对的游戏版本，因此当前所有结果 `training_eligible=false`。

现有训练入口仍受 `lab/rl_contract.py` 的独立实战校准门槛限制；网页导入不会启动训练，也不会向训练数据集写入内容。

## 网页与本机 API

在 `/battle` 使用“粘贴阵容码”，多条码每行一条。先逐条查看结果和问题，再选择导入我方或对方。原码和解析依据随阵容模板、对局导出保存；后续编辑不会覆盖原始解析证据。


- `POST /api/team-code/parse`：`{"code":"…"}`，单条解析。
- `POST /api/team-codes/parse`：`{"text":"…"}`，每行一条，返回原行号与独立解析结果。
- `POST /api/opponent/recognize`：`{"text":"火羽，罗隐"}`，仅名称/游戏 ID 匹配，不补隐藏配置。
- `POST /api/opponent/search`：同上，在用户提供的阵容库中做包含筛选，返回可点击候选及全部诊断。

这些接口只读图鉴与阵容库、无磁盘写入。来源跨站请求会被拒绝。客户端传来的“已合法”“可训练”等标志不作为解析依据。

# 候选配招槽位的推断边界

阵容码之外，联合候选推断也必须保留四个技能槽及空槽 `0`；不再排序或去重。重复非空技能和超过四槽的候选会报错，不能静默修正。空槽不会出现在“携带技能概率”中，但会保留在已知槽位的概率分布中。

推断存档现为 schema 3，继续保留 schema 2 引入的槽位信息，并新增离散伤害观测。旧 schema 1 曾经对技能数组排序并去重，已丢失的信息无法恢复；读取时保留现有数组，并明确 `move_slots_known=false`。不足四槽的旧候选同样不补槽。只有所有非零概率候选都提供完整已知槽位，才输出 `move_slot_marginals`。旧版超过四槽的候选需要重新核对，原文件不会被修改。
